# راهنمای داده

این سند برای کسی نوشته شده که می‌خواهد داده‌های بانک‌رادار را ویرایش، گسترش یا واکشی کند.

## ساختار پرونده‌ها

| پرونده | نقش | دستی ویرایش می‌شود؟ |
| --- | --- | --- |
| `data/products.json` | منبع حقیقت محصولات | بله |
| `data/banks.json` | فهرست بانک‌ها و مؤسسات مجاز | بله |
| `data/indicators.json` | شاخص‌های کلان و نرخ‌های مرجع | بله |
| `data/schema.json` | طرح‌واره اعتبارسنجی | با احتیاط |
| `data/meta.json` | گزارش آخرین اجرای خط لوله | خیر — بازنویسی می‌شود |
| `data/bundle.js` | بسته درون‌خطی برای بارگذاری در مرورگر | خیر — ساخته می‌شود |

## چرخه به‌روزرسانی

```
tools/collect.mjs   →   data/products.json   →   tools/build-bundle.mjs   →   data/bundle.js
        ↑                        ↓
   منابع بیرونی        scripts/validate-data.mjs  (دروازه کیفیت)
                                 ↓
                    tools/data-signature.mjs  (دروازه «تغییر واقعی»)
```

هر اجرا ابتدا داده موجود را می‌خواند، سپس یافته‌های تازه را **روی** آن ادغام می‌کند.
ترتیب و قواعد ادغام در ادامه آمده است.

پیش از ثبت در مخزن، دو دروازه باید رد شوند: اعتبارسنجی (داده معیوب ثبت نمی‌شود) و
مقایسه امضای محتوایی (اجرای بی‌نتیجه، کامیت بی‌محتوا نمی‌سازد).

## قواعد ادغام

خط لوله هرگز داده‌ای را حذف نمی‌کند. رفتار دقیق:

**رکورد دست‌نویس** (بدون `autoDiscovered`) در برابر بازنویسی محافظت‌شده است. اگر منبع بیرونی
محصولی با همان شناسه یا همان کلید `bank::product` پیدا کند، تنها این فیلدها به‌روز می‌شوند:

```
lastSeen، source.checked، و در صورت تغییر واقعی: rate، amountLabel، termLabel
```

فیلدهای ساختاری زیر هرگز بازنویسی نمی‌شوند، چون حاصل قضاوت انسانی‌اند:

```
id، category، subcategory، benefit، speed، digital، friction،
collateralKind، confidence، regulatory، source(kind/title/url)، lastUpdated
```

**رکورد خودکار** (با `autoDiscovered`) با کلید `bank::product` تطبیق داده می‌شود — نه با
شناسه، چون شناسه ممکن است در منبع تغییر کند و آن‌وقت رکورد تکراری ساخته می‌شود.

**رکورد دیده‌نشده** حذف نمی‌شود؛ فقط `stale: true` می‌گیرد و در رابط کاربری با نشان
«نیازمند بازبینی» نمایش داده می‌شود.

## افزودن یک محصول دستی

۱. رکورد را به آرایه `products` در `data/products.json` بیفزایید.
۲. `data/schema.json` را ببینید تا همه فیلدهای لازم را بدانید.
۳. اعتبارسنجی کنید:

```bash
node scripts/validate-data.mjs
```

۴. بسته را بازسازی کنید تا در مرورگر دیده شود:

```bash
node tools/build-bundle.mjs
```

### نکات مهم در نوشتن رکورد

**`rate` و `rateKind` با هم معنا پیدا می‌کنند.** برای وام قرض‌الحسنه، عدد ۴ در فیلد `rate`
یک *کارمزد* است، نه سود — پس `rateKind: "fee"`. این تفاوت در امتیازدهی و در ماشین‌حساب
اقساط اثر مستقیم دارد: موتور مالی کارمزد را به‌عنوان هزینه افزوده محاسبه می‌کند.

**`collateralKind` را دقیق انتخاب کنید.** مقدار `deposit-block` جریمه امتیازی می‌گیرد
(هزینه فرصت پول خوابیده). اگر وامی سپرده می‌خواهد اما مسدود نمی‌کند، `mixed` مناسب‌تر است.

**`confidence` را صادقانه بگذارید.** `high` یعنی رقم را از منبع رسمی همان بانک دیده‌اید.
`medium` یعنی از رسانه یا مرجع مقایسه‌ای نقل شده. `low` یعنی اطلاعات قدیمی است یا
تأیید مستقل ندارد. این فیلد مستقیماً در امتیاز اثر می‌گذارد — پس بالا بردن بی‌دلیل آن،
خروجی سامانه را گمراه‌کننده می‌کند.

**`contractType` اختیاری است اما اگر منبع رسمی نوع عقد را می‌گوید، ثبتش کنید.**
مقادیر: `qarz` (قرض‌الحسنه)، `non-partnership` (عقود غیرمشارکتی/مبادله‌ای)، `partnership`
(عقود مشارکتی)، `unknown`. اگر فیلد را بگذارید، سامانه دقیقاً همان را به کار می‌برد و
فیلتر «نوع عقد» در دسته‌های تسهیلات و اعتباری از همین تفکیک استفاده می‌کند. در نبود
این فیلد، نوع عقد به‌صورت قطعی از خود رکورد استنتاج می‌شود:

| نشانه در رکورد | نتیجه استنتاج |
| --- | --- |
| `rateKind: "fee"` | `qarz` — کارمزد یک‌بار یعنی قرض‌الحسنه |
| ذکر «قرض‌الحسنه» در عنوان/توضیحات با نرخ ≤ ۱۰٪ | `qarz` |
| ذکر «مشارکت» یا «مضاربه» در تسهیلات سودمحور | `partnership` |
| سایر تسهیلات سودمحور | `non-partnership` — مبنای معقول: غلبه عملی عقد مبادله‌ای و سقف‌های مصوب |
| غیرنرخ‌دار (مثل باشگاه مشتریان) | `unknown` — ادعایی شکل نمی‌گیرد |

برای رکوردهای جدیدِ دست‌نویس توصیه می‌شود `contractType` صریح بگذارید؛ استنتاج، راه
پس‌روی برای داده‌هایی است که از منبع بیرونی یا دستی با جزئیات ناکافی می‌رسند.

## افزودن منبع واکشی تازه

منابع در `tools/sources/` قرار دارند. هر منبع یک فایل ماژول است که آرایه‌ای از محصولات
برمی‌گرداند:

```js
// tools/sources/example.mjs
import { runSource } from '../lib/http.mjs';

export async function collect() {
  return runSource('example', async ({ get, log }) => {
    const html = await get('https://example.ir/loans');
    // ... استخراج
    return products;
  });
}
```

سپس در `tools/collect.mjs` به فهرست منابع اضافه شود. نکته مهم: `runSource` خطای منبع را
می‌گیرد و در `meta.json` ثبت می‌کند، بنابراین شکست یک منبع کل خط لوله را متوقف نمی‌کند.

### اصل طراحی: استخراج بر پایه برچسب

صفحات مقایسه‌ای معمولاً جدولی از «برچسب → مقدار» دارند. استخراج را روی **متن برچسب** بنا
کنید، نه سلکتور CSS:

```js
// شکننده — با هر بازطراحی می‌شکند
const rate = $('.spec-table tr:nth-child(3) td:nth-child(2)').text();

// مقاوم — برچسب‌ها پایدارترند
const rate = findSpec(html, 'نرخ سود وام');
```

تابع `extractSpecTable` در `tools/sources/rade.mjs` این کار را انجام می‌دهد و
`tests/merge.test.mjs` رفتارش را قفل کرده است.

## دروازه کیفیت

`scripts/validate-data.mjs` این موارد را بررسی می‌کند و در صورت خطا با کد ۱ خارج می‌شود:

- انطباق با طرح‌واره: فیلدهای الزامی، نوع داده، بازه مقادیر
- یکتایی شناسه‌ها
- هم‌خوانی `counts` با تعداد واقعی
- وجود `source.url` معتبر در همه رکوردها
- قالب درست تاریخ `lastUpdated`
- معتبر بودن دسته و زیر‌دسته

این اسکریپت در هر سه جریان کاری CI اجرا می‌شود و **مانع انتشار داده معیوب** است.
اگر خط لوله خودکار داده‌ای تولید کند که از این دروازه رد نشود، آن داده هرگز commit نمی‌شود
و سایت با آخرین نسخه معتبر به کار خود ادامه می‌دهد.

## دروازه دوم: امضای محتوایی داده

`tools/data-signature.mjs` اثر انگشت ۱۶ نویسه‌ای از محتوای داده می‌سازد:

```bash
node tools/data-signature.mjs                 # فقط امضا
node tools/data-signature.mjs --json          # امضا + شمارش محصولات/بانک‌ها/شاخص‌ها
node tools/data-signature.mjs --field=products # تک‌مقدار برای مصرف در شل
```

امضا این‌ها را **در بر می‌گیرد**: رکوردهای محصولات (همه فیلدها، از جمله `lastSeen`،
`lastVerified` و `stale`)، شاخص‌های کلان، بازه‌های مصوب، مقدارهای مشتق و فهرست بانک‌ها.

و این‌ها را **نادیده می‌گیرد**: `generatedAt` در `products.json` و `lastRun`،
`lastRunDurationMs` و گزارش منابع در `meta.json`.

دلیل: این فیلدها در هر اجرا عوض می‌شوند، پس `git diff` همیشه پر است. اگر ملاک کامیت
همان diff باشد، هر اجرای ناموفقِ شبکه هم یک کامیت و یک انتشار بیهوده می‌سازد و
تاریخچه مخزن پر از نویز می‌شود. با امضا، کامیت فقط وقتی ساخته می‌شود که واقعاً
مقداری عوض شده باشد یا رکوردی بازبینی شده باشد.

`tests/signature.test.mjs` هر دو سمت این قرارداد را قفل کرده است: بی‌حسی به مهرهای
زمانی و حساسیت به هر تغییر محتوایی.
